GO CORE
Packages define boundaries; keep them cohesive and avoid import cycles. Interfaces are implicit, small, and usually defined near the consumer. Prefer composition over inheritance. Errors are values: return, wrap with %w, inspect with errors.Is/As, and map at transport boundaries. panic is not normal error flow; recover only at controlled boundaries. defer is for cleanup, but understand execution order and loop cost.

Slices reference an underlying array; append may reallocate. Maps are unsafe for concurrent writes. Use pointer receivers for mutation, large structs, or method-set consistency. Prefer useful zero values.

CONTEXT / LIFECYCLE
context.Context carries cancellation, deadlines, and request-scoped metadata; it is not DI or a general parameter bag. Pass it first from transport through service, DB, and external clients. Cancellation is cooperative. A shared context does not cancel sibling goroutines automatically on error; use explicit cancel or errgroup.WithContext.

Graceful shutdown: receive SIGTERM/SIGINT, cancel root context, stop new requests, call server.Shutdown with timeout, stop workers, wait for goroutines, flush telemetry, then close DB/resources. Every long-lived goroutine needs an owner, cancellation path, error strategy, and join mechanism.

CONCURRENCY
A goroutine is a lightweight runtime-scheduled task, not one OS thread or a Task object. Channels coordinate ownership, pipelines, signalling, and backpressure; mutexes protect small shared-state critical sections. WaitGroup only waits; it does not return errors or cancel siblings. errgroup is better for concurrent tasks with error propagation and shared cancellation.

Bound concurrency with worker pools, buffered channels, or semaphore. Avoid unlimited goroutines. Typical failures: leaks from blocked send/receive, double close, races, holding locks during network calls, lock-order problems, and ignored cancellation. Verify with go test -race, cancellation/timeouts, and load tests.

HTTP / REST
Handler parses and validates transport input, calls service, and maps result/errors. Business rules belong in service/domain, not only middleware. Middleware is for auth, logging, tracing, recovery, request IDs, and coarse authorization. Use DTOs instead of exposing persistence models. PATCH must distinguish absent from explicit zero/false, often with pointers. For long work return operation ID/status and use polling, callback, or events.

GRPC / PROTOBUF
.proto defines package, messages, enums, services, and RPC methods. protoc plus Go plugins generates message types and client/server interfaces; business logic implements the generated server interface. Know unary, server-streaming, client-streaming, and bidirectional streaming. Use context deadlines, metadata, interceptors, and status/codes.

Protobuf is compact because fields use numeric tags and binary encoding with generated serializers. gRPC commonly uses HTTP/2 multiplexing and persistent connections, but is not always faster; REST may also use HTTP/2. Compatibility: never reuse removed field numbers, reserve them, add fields compatibly, and avoid breaking method semantics. Retries must be bounded and safe; non-idempotent RPCs require idempotency protection.

GORM / POSTGRESQL
GORM is an ORM/toolkit, not a substitute for SQL. Use explicit models/tags, transactions, migrations, indexes, constraints, and WithContext. Watch N+1; use joins/preload selectively and inspect SQL. Use raw SQL when clearer or more efficient. Configure connection pool limits and lifetime.

Transaction boundary belongs in the service/use case that owns the business operation. Keep transactions short and avoid slow external calls inside them. Enforce invariants with unique constraints and conditional updates. Avoid SELECT active -> later UPDATE; use atomic UPDATE ... WHERE id=? AND active=true and check RowsAffected, or use locking/versioning. Optimistic locking fits low conflict; SELECT ... FOR UPDATE protects critical rows. Diagnose with EXPLAIN ANALYZE and indexes matching real filters/order.

Migrations should be ordered, deployable, and backward-compatible for rolling releases. Soft delete supports history but requires consistent visibility filters. Audit fields record who, when, and what changed.

FINANCIAL RELIABILITY
Idempotency prevents duplicate effects. Store idempotency key + request fingerprint + result/status under a unique constraint. Use explicit states such as Pending, Processing, Succeeded, Failed, RequiresReview. Retry only transient failures with bounded exponential backoff and jitter. Do not retry validation errors blindly.

Callbacks/webhooks must be authenticated, deduplicated, order-tolerant, and safe when repeated. Reconciliation compares internal and external state and flags or repairs divergence. Audit trail records transitions. Transactional outbox can atomically save a business change and an event, then publish asynchronously. Eventual consistency is acceptable when status is visible. Mask secrets and PII; use correlation IDs.
