LATEST PROJECT - CANONICAL STORY
The product was an insurance and document-management platform for claims, documents, checks, decisions, and audit-oriented workflows. It already contained ASP.NET Core backend components and web applications.

A separate financial application, owned by another team, communicated with banking APIs. The insurance platform needed a controlled integration boundary to exchange validated data and operation statuses with that system. We introduced a Go service:
Insurance platform -> Go integration service -> external financial application -> banking APIs.

The Go service did not act as a bank and did not replace the external financial application. It accepted requests from the insurance platform, validated and normalized data, mapped internal DTOs to REST/protobuf contracts, called the external application, stored correlation IDs and operation state, handled callbacks or asynchronous results, and returned a stable result to the insurance workflow.

MY GO WORK
I worked with explicit dependency wiring, HTTP handlers, middleware, services/use cases, repositories, integration clients, DTO/protobuf mapping, PostgreSQL/GORM, SQL migrations, status transitions, correlation IDs, context propagation, timeouts, retries, background workers, structured logging, tests, and integration diagnostics.

Typical synchronous flow: request -> validation -> service -> DB transaction -> external client -> persisted status -> response. For long operations: save Pending -> bounded worker -> external call/callback -> update final status -> expose result. Context travelled from handler to service, DB, and external calls. Critical updates had to be atomic; retries had to be bounded and duplicate-safe.

AI / LLM
Insurance-document flow: ingestion -> extraction/normalization -> chunking -> retrieval -> prompt -> structured output -> citations and deterministic validation -> confidence/evaluator checks -> human review. Python FastAPI/LangChain acted as an AI sidecar. Go/.NET services controlled orchestration, authorization, persistence, validation, and business actions. LLM output was advisory and could not autonomously approve a claim or execute a financial operation.
